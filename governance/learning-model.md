# Учебно-инженерная модель Enterprise Cybersecurity Program

## 1. Что является результатом обучения

Результатом считается не прочитанный материал и не заполненная таблица, а воспроизводимая часть Enterprise Cybersecurity Lab, подтверждённая тестами и evidence.

Каждый PXX должен оставить:

- работающую capability;
- безопасно воспроизводимый лабораторный сценарий;
- технические артефакты ролей;
- Run A и сопоставимый Run B;
- расследование и root cause;
- remediation;
- recovery/rollback proof;
- Assurance decision;
- public-safe case study.

## 2. Двухпроходная теория

### Проход 1. Целостная теория текущего PXX

До основной практики пользователь:

- полностью читает основную литературу, назначенную текущему проекту;
- полностью читает назначенные диапазоны в книгах, которые шире проекта;
- проходит обязательные статьи и видео;
- формирует общую модель системы, терминов, ролей, угроз и технологий;
- отвечает на вопросы самопроверки.

Полное чтение относится к основному маршруту текущего проекта. RFC, command reference, man pages, API reference и альтернативные материалы не обязаны читаться целиком заранее.

### Проход 2. Теория перед действием

Перед каждой практической фазой повторяются:

- релевантные страницы книг;
- официальная документация;
- стандарт или спецификация;
- источник практики;
- команды, параметры, критерии результата и типовые ошибки.

После повторения сразу выполняется действие в LAB.

## 3. Единица работы

`источник → понимание → план → действие → фактический результат → проверка → evidence → вывод`

Каждый evidence record содержит минимум:

- source;
- expected result;
- action/configuration;
- actual result;
- timestamp UTC;
- tool and module versions;
- hashes where applicable;
- conclusion;
- next action or handoff.

## 4. Проектный цикл

### 4.1 Проектирование

Фиксируются:

- цель и capability;
- активы;
- архитектура;
- trust boundaries;
- inventory;
- threat model;
- применимые роли;
- acceptance criteria;
- test strategy;
- evidence plan;
- recovery plan.

### 4.2 Baseline

- Delivery разворачивает штатную систему.
- Defense применяет исходные контроли и телеметрию.
- Assurance проверяет функциональность и готовность.
- Recovery создаёт и проверяет recovery point.

### 4.3 Run A

Attack выполняет реалистичный сценарий в пределах LAB. Защита не получает искусственного преимущества. Investigation собирает и анализирует фактические артефакты. Assurance фиксирует исходный результат.

### 4.4 Investigation и root cause

Выполняются:

- chain of custody;
- hash and integrity checks;
- UTC timeline;
- PCAP/log/host artifact analysis;
- facts versus hypotheses;
- affected scope;
- root cause;
- containment and residual risk.

### 4.5 Remediation

Роли устраняют первопричину, добавляют защитные меры, detection, тесты, документацию и recovery steps.

### 4.6 Run B

Используется сопоставимый сценарий:

- те же цели и scope;
- зафиксированные версии;
- сопоставимые входные данные;
- тот же набор основных техник;
- заранее определённые критерии сравнения.

### 4.7 Recovery и regression

Проверяются backup, restore, rollback, service health, idempotence, regression, RTO/RPO и отсутствие незадокументированных ручных действий.

### 4.8 Assurance gate

Статусы:

- `PASS`;
- `FAIL`;
- `BLOCKED`;
- `NEEDS_REVIEW`.

Следующий PXX не считается открытым до PASS предыдущего обязательного gate.

## 5. Роли

В P00–P18 все R01–R26 должны быть явно рассмотрены. Применимая роль получает:

- теорию;
- практику;
- инструментальный маршрут;
- реальную задачу;
- артефакт;
- тест;
- evidence;
- handoff.

Роль нельзя засчитать только по упоминанию её названия. Глубина работы определяется scope проекта, но качество выполнения не снижается искусственно.

## 6. Источники практики

Для каждого практического действия указывается конкретный внешний источник:

- официальная пошаговая документация;
- лабораторная;
- workshop;
- challenge;
- курс;
- репозиторий с упражнениями;
- известная уязвимость или бывшая zero-day;
- поддерживаемая ATT&CK-практика;
- исследовательская методика.

Авторская адаптация допускается, но исходный источник и границы адаптации сохраняются.

## 7. Язык источников

- Приоритет: русскоязычный официальный материал или качественный технический перевод/разбор.
- Англоязычный первоисточник сохраняется для точности и проверки.
- Отсутствие русского пути должно быть явно отмечено как gap.

## 8. Административный и учебный слои

### Учебно-технический слой PXX

Содержит только то, что нужно для изучения, выполнения, проверки и защиты проекта:

- теория;
- практика;
- инструменты;
- архитектура;
- технический манифест;
- роли;
- Run A/Run B;
- recovery;
- evidence;
- PASS criteria;
- портфельные результаты.

### Административный слой

Хранит отдельно:

- ACTIVE-версии;
- миграции;
- аудиты;
- статусы программы;
- market mapping;
- общие release policies;
- историю изменений;
- управление библиотекой.

Административная информация не должна вытеснять теорию и практику из PXX.

## 9. Портфолио

Публичный репозиторий содержит безопасную проекцию выполненной работы:

- architecture;
- ADR;
- contracts;
- code;
- tests;
- detection content;
- sanitized fixtures;
- Run A/Run B comparison;
- case study;
- limitations.

Полные PCAP, dumps, malware, snapshots, credentials, private keys, production data и другие sensitive artifacts остаются в private evidence vault.

## 10. Честность статуса

- `DESIGNED` не означает `IMPLEMENTED`.
- `IMPLEMENTED` не означает `LAB_VALIDATED`.
- `LAB_VALIDATED` не означает `PASS`, пока не выполнены независимые критерии Assurance.
- Лабораторная практика не выдаётся за коммерческий production-опыт.
